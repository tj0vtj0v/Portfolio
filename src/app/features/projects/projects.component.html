How it started

A few months into my vocational training, our instructor showed us how to build a small application with a database, an API, and a “quickly” built frontend.

After two years of building, rebuilding, and taking a few breaks along the way, the first usable version went online. It ran on a Raspberry Pi in my student room, with Expense Tracker as the first working tool.

Learning by rebuilding

Over the next year, I fixed bugs and rewrote the backend using what I’ve learned. The result was a more stable API with a structure that was easier to expand. I also added database versioning to keep track of changes.

Now, four years after starting, I’d say it’s almost finished. With a proper user interface and the portfolio and Workspace filled out, it’s finally close to what I had in mind.

Three-layer architecture

The website is built in three layers: the frontend is what you see and interact with, the API handles requests and application logic, and the database stores the data. Keeping them separate lets me work on each part independently, as long as the interfaces between them stay compatible.

Your account and data

The portfolio is public, while the Workspace requires an account. The API checks who is signed in so each user can only access their own saved data.

Passwords are stored as hashes rather than readable text. This lets the API verify a password at login without storing the original password.

Continuous Deployment

When my internet provider stopped offering fixed IP addresses, I moved the website from my Raspberry Pi to a virtual private server at IONOS. Thanks to Docker, the move was easier than I expected. After transferring the database, it ran pretty much on the first try.

When I push changes to the main branch, GitHub Actions automatically builds and deploys the frontend. Docker Compose manages the services and runs them together.

I joined Fast Forest’s driverless department in April 2024. Since then, I’ve developed our camera perception and global mapping systems and supervised the development of our LiDAR perception. Together, these systems let the car detect cones, map the track, and locate itself within it.

The competition environment

Formula Student tracks are marked with cones. The driverless car needs to detect where they are in real time to find its way around the course.

All of this has to run reliably on the car’s onboard computer, so we can push the car towards its physical limits while keeping it safe.

Our driverless system concept

All processing runs on a Jetson AGX Orin, where five loosely coupled containers exchange data to turn sensor readings into control commands. These commands are then sent to the car over the CAN bus.

Camera perception detects the cones marking the track. These detections feed into the mapping module, which uses simultaneous localisation and mapping (SLAM) to build a map and locate the car within it. The drive controller then plans a trajectory using either local observations or the map. From there, the steering controller and power electronics ECU carry out the commands to steer and drive the car.

Camera Perception

From stereo images to cone positions relative to the car.

  • C++
  • TensorRT
  • OpenCV
  • YOLO26

The camera system turns images into a local 2D map of the cones around the car. Detection finds the cones in the images, and projection estimates their positions using the size of the detected cones.

The camera setup

We use a stereo camera that provides synchronized left and right images. These are processed on the car’s onboard computer using C++ and OpenCV, with TensorRT handling neural network inference.

Developing and testing the camera perception system involved plenty of debugging before it was ready to run on the car. Most of that work went into reducing latency, improving projection accuracy, and integrating TensorRT’s NvInfer library.

Detection: finding cones in the image

A YOLO26 model detects cones and marks them with bounding boxes. To help it detect cones both nearby and farther away, we combine a scaled-down overview of the camera image with a detailed crop of its centre.

Both views fit into a single model input, keeping processing costs low, which is the main constraint when running detection onboard. The illustration below shows how the image is prepared.

The overview keeps the full field of view for tight corners, while the central crop preserves the detail needed to detect cones farther down the track. We use a 960 × 960 model input to fit both views, balancing detection accuracy with processing time.

To reduce jitter in the bounding boxes, we run detection on slightly modified versions of the same image. We then match detections of the same cone and average their boxes, giving us more stable estimates of the cone positions.

Projection: from pixels to cone positions

To estimate where a cone is relative to the car, we first map its bounding box back to the original camera image. From there, we use the cone’s known size and how large it appears in the image to estimate its distance. Its position in the image gives us the viewing angle, allowing us to calculate its position relative to the car.

Each camera gives us its own estimate of the cone positions. We combine these into one local map by matching observations of the same cone and averaging their positions.

Mapping Module

Building a map of the track and locating the car within it.

  • C++
  • Graph SLAM
  • EKF
  • g2o

The mapping module builds a map of the track as the car drives, combining detected cones with estimates of the car’s movement. It provides this map and the car’s position within it to the drive controller, which uses them to plan the car’s path.

Building and correcting the map

Neither the detected cone positions nor the movement estimates are exact, so errors can build up as the car drives. Graph SLAM connects the car’s past positions and the observed cones in a graph, allowing new observations to correct earlier estimates and keep the map consistent.

To keep processing times short, each update only optimises the most recent part of the graph. After a completed lap, the system optimises the full graph, using cones it has seen before to correct the accumulated drift across the track.

Localisation in real time

Correcting the map takes time, especially when the car completes a loop and optimises the full map. In the worst case, this takes 100 ms. At our top speed of 38 m/s, the car travels 3.8 metres in that time, so its position needs to be updated more often.

An extended Kalman filter handles these faster position updates separately, using the latest SLAM map together with incoming perception and motion estimates. This keeps the drive controller updated while graph optimisation runs in the background.

Current state of development

The SLAM system remains in active development and has already been successfully tested on the car. Next, we plan to integrate a ground-speed sensor to improve motion estimates between updates.

On the first lap of an unknown track, the system builds the map by adding newly detected cones as landmarks.

3. Finished

With a fixed map, the system only updates the car’s position. The map is either predefined or built during earlier laps, depending on the discipline: Autocross, Trackdrive, or Skidpad.

Skidpad Localization

The Skidpad layout is fully defined by the rulebook, so we can use a predefined map without having to build it first. Our previous approach used a single EKF to locate the car, but its position estimate could jump one cone pair forwards or backwards because of the repetitive layout. The graph fixes this by keeping a short history of measurements to stabilise localisation. Since switching, we haven’t seen those jumps.

Multispectral Aerial Mapping

A pipeline that turns multispectral drone data into a georeferenced map.

  • DJI 3E
  • Python
  • WebODM
  • WebDAV
  • Docker

Processing on limited hardware

The pipeline starts on a device with limited computing power. After a completed drone mission, inserting the SD card automatically starts the program. It checks and sorts the metadata, RGB images, and multispectral images, then compresses everything and uploads it to Nextcloud over WebDAV.

A separate processing machine checks for new uploads, downloads the data, and runs the mapping jobs. Once processing is finished, it uploads the resulting maps back to Nextcloud.

Mapping result

The WebODM setup processes the RGB and multispectral images separately. The two outputs are then combined into a single GeoTIFF containing both the visual map and the multispectral data.

The combined file can then be used for further analysis, such as calculating NDVI from the red and near-infrared bands to show differences in vegetation.

Future application

This pipeline lays the groundwork for applying research from the Applied AI group in Grafenau to analysing drone imagery. The group currently uses hyperspectral satellite images, including data from CRISM, to classify minerals on the surface of Mars.

The idea is to use similar methods with drone data for commercial applications here on Earth.

Self-built VTOL

Long-term project combining robotics, flight, and aerial mapping.

Concept stage

What is a VTOL?

VTOL means vertical take-off and landing. A fixed-wing VTOL takes off like a drone, then flies like a plane. This allows it to cover longer distances efficiently without needing a runway.

I want to build the whole system myself, from the airframe and electronics to the software. It’s a project where I can use what I’ve learned so far and figure out the parts I don’t know yet.

The scope

The plan includes designing and building the airframe, developing the PCBs, and integrating cameras and a LiDAR. An additional power supply and a Jetson will support the computing needed for autonomous navigation later on.

The long-term goal is an autonomous aerial platform for collecting data and trying out different sensors and ideas. For now, the project is still at the concept stage, with initial designs in place and the detailed requirements still being worked out.
