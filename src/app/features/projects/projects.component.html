How it started

A few months into my vocational training, our instructor showed us what we could build with a simple database, an API, and a “quickly” built frontend.

After two years of building, rebuilding, and taking a few breaks along the way, the first usable version went online. It ran on a Raspberry Pi in my student room, with Expense Tracker as the first tool ready to use.

Learning by rebuilding

Over the next year, I fixed bugs, rewrote the backend, and learned from the mistakes I'd made. The result was a more stable API with a structure that was easier to expand and a versioned database that made changes easier to manage.

Now, four years after starting, I almost consider it finished. With a proper user interface and content across the portfolio and Workspace, it's finally becoming the website I had in mind.

Three-layer architecture

The website is built in three layers: the frontend handles what you see and interact with, the API handles requests and application logic, and the database stores the data. They are loosely coupled, so I can develop each part separately as long as the interfaces between them stay compatible.

Your account and data

The portfolio is public, while the Workspace requires an account. The API checks who is signed in so each user can only access their own saved data.

Passwords are stored as hashes rather than readable text. This lets the API verify a password at login without storing the original password.

Continuous Deployment

When my internet provider stopped offering fixed IP addresses, I moved the website from my Raspberry Pi to a virtual private server at IONOS. The Docker setup made the move surprisingly straightforward: after transferring the database, the application was up and running pretty much on the first try.

Today, GitHub Actions automatically builds and deploys the frontend when changes reach the main branch. Docker Compose manages the services and runs them together.

Formula Student

Meet the team ↗

Formula Student is an international engineering competition where students design, build, and race their own cars each year. Fast Forest is the team at the Deggendorf Institute of Technology.

I joined Fast Forest's driverless department in April 2024. Since then, I've developed our camera perception and global mapping systems and supervised the development of our LiDAR perception. Together, they help the car perceive its surroundings and understand the track.

The competition environment

Formula Student tracks are marked with cones. To navigate the course, the driverless car needs to detect and locate them accurately in real time.

The challenge is doing all of that on the car's onboard computer, reliably enough to push towards its physical limits while keeping it safe.

Our driverless system concept

All processing runs on a Jetson AGX Orin. Five loosely coupled containers exchange data, with control commands sent to the car over the CAN bus.

Camera perception detects the cones marking the track. Using simultaneous localisation and mapping (SLAM), the mapping module builds a map and locates the car within it. The drive controller plans a trajectory from local observations or the map. Finally, the steering controller and power electronics ECU execute the commands.

Camera Perception

From stereo images to cone positions relative to the car.

The camera pipeline has two main tasks: the detection finds cones in the images, and the projection converts those detections into positions the rest of the driverless stack can use.

The camera setup

The pipeline retrieves stereo images through the ZED SDK. Its C++ implementation uses OpenCV for image processing and TensorRT to run the neural network efficiently on the Jetson.

I developed, validated, and deployed the camera perception system, which involved plenty of debugging and fixing integration issues. The biggest challenges were reducing latency, increasing projection accuracy and integrating TensorRT's NvInfer library.

Detection: finding cones in the image

A YOLO26 model detects cones and marks them with bounding boxes. Before inference, each camera image is prepared to give the model both an overview and a more detailed view.

The illustration below shows how we make the most of the model input. Combining the overview and a detailed crop gives the model both views in a single input, keeping the processing cost low.

The overview preserves the field of view, while the crop keeps the original sensor resolution in the centre of the image. This lets us detect cones across the image while retaining more detail for distant cones. We settled on a 960 × 960 model input as a practical balance between latency and accuracy with the benefit of an convenient layout.

To reduce random jitter in the bounding boxes, we also run multiple batches with augmented versions of the image. We overlay the results, match boxes belonging to the same cone, and average them to get more stable detections and therefore projections.

Projection: from pixels to cone positions

A bounding box tells us where a cone appears in an image, but the car needs its position relative to itself. First, we transform the detections from the resized and cropped model input back into the original image coordinates.

We estimate the distance using the cone's known size, the camera's field of view and resolution, and the dimensions of the bounding box. The cone's centre in the image gives us its angle relative to the camera. Together, these give us a local cone position.

When using both stereo images, we merge the local map of both cameras by matching cones one to one and averaging their positions.

Finding a place
in a map we already know.

Mapping and localisation solve different parts of the problem. When a map already exists, the task is to estimate where the car is within it, using its movement and the landmarks it can currently see.

The skidpad is a useful example: its known cone layout provides a reference for the vehicle's position. The visualisation separates fixed landmarks, graph edges, fixed and active poses, and the field of view.

My module can load a predefined map and begin in its finished-map mode, so it can work with an existing map as well as build a new one.

From drone mission
to mapped fields.

I built a pipeline that turns the data from a DJI drone mission into structured inputs for automated mapping.

The client detects a completed flight on the removable storage, separates metadata, RGB, and multispectral data, compresses the folders, and uploads them to Nextcloud over WebDAV. A server-side listener picks up complete flights and passes the data to a WebODM container.

Mapping as a repeatable handoff

WebODM processes both visual and multispectral image sets. When processing finishes, the pipeline combines the orthophotos, produces the requested image outputs, and uploads the mapping products back to the same cloud workspace.

NDVI is derived from the TIFF's multispectral red and near-infrared bands. Both views use the same alpha mask and downscaled map extent.

A VTOL of my own.

A planned research platform for robotics and aerial mapping.

Concept stage

What is a VTOL?

VTOL means vertical take-off and landing. A fixed-wing VTOL combines vertical lift for take-off and landing with a wing that carries the aircraft during forward flight. The idea is to explore longer flights without needing a runway.

For me, it is a way to connect airframe design, electronics, robotics, and geoinformatics in one project that I can build and understand from the ground up.

The scope

I want to design and manufacture the airframe, develop the PCBs, and integrate sensors such as cameras and LiDAR. A Jetson Orin is a candidate for onboard computing.

The longer-term goal is a platform for autonomous flight experiments and aerial mapping. Airframe construction, electronics integration, sensor processing, and flight experiments are separate parts of that path; the project is currently at the concept stage.
